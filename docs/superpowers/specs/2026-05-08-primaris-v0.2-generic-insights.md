# Primaris v0.2.0 — Generic + Insights-Driven Design

**Date**: 2026-05-08
**Author**: Bach (TruongBach) + Claude (Opus 4.7)
**Status**: Approved (sections 1-7)
**Prior version**: v0.1.0 — Phase 1 (Bach-personal, ticket-pipeline-driven)
**Successor target**: v0.2.0 — Phase 1.5 (generic, `/insights`-driven)

---

## Vision shift

v0.1.0 tied primaris to one user (Bach) and one data source (`.imperium/runs/<ticket-id>/log.md`). It worked, but it was not portable. v0.2.0 turns primaris into a **shareable AI Engineering OS** that any Claude Code user can install, configure for themselves, and use as a self-coaching loop.

Two structural changes drive the rework:

1. **Generic identity** — no hard-coded user name. Plugin ships a template; each user fills it on first run.
2. **`/insights`-driven scoring** — Cawl's primary data source becomes the Claude Code built-in `/insights` report (`~/.claude/usage-data/report.html`). The report aggregates 21 days of session metrics, friction patterns, project areas, and concrete suggestions — exactly the rubric Cawl needs. The existing ticket-pipeline run artifacts remain a supplemental source, not the primary.

The doctrine, the level rubric, and the prime-directive playbook are already generic and remain unchanged.

## Scope (v0.2.0 only)

**In scope**

- Cawl rewrite: primary input becomes `~/.claude/usage-data/report.html`. Workflow extracts metrics from the report's HTML sections.
- `/level-check` rewrite: check report freshness (mtime ≤ 7 days). If stale or missing, instruct the user to run `/insights` first. Then spawn Cawl.
- User-data path: `~/.primaris/growth-plan.md` (and other future user files). Resolved from env `PRIMARIS_HOME` (default `~/.primaris`).
- `growth-plan.template.md` shipped in the plugin. `bach-growth-plan.md` removed.
- Levels rubric extended: per-level **Roadmap** subsection (Readiness signals / Upgrade actions / Common blockers).
- README and doctrine de-Bach. Plugin description in `marketplace.json` updated.
- Plugin version bump 0.1.0 → 0.2.0.
- ROADMAP entry for v0.2.0.

**Out of scope (deferred)**

- Phase 2 — Prime Directive enforcement (skills `investigate`, `repro-first`, `scope-guard`). Same Phase 2 as before.
- Phase 3 — Hard hooks. Same as before.
- Phase 4 — Workflow library. Same as before.
- Auto-running `/insights` from inside `/level-check` (slash commands cannot invoke other slash commands; user runs `/insights` themselves when prompted).
- Native HTML rendering of Cawl's eval reports. Plain markdown only.
- Multi-user installations on the same machine. One user per `PRIMARIS_HOME`.

## Architecture

### Data source priority

Cawl reads in this order, using whichever is available:

1. **Primary**: `~/.claude/usage-data/report.html` — Claude Code `/insights` output. Required for v0.2.0 default flow.
2. **Supplement**: `.imperium/runs/<ticket-id>/{state.json,log.md}` — for ticket-pipeline-driven runs (per-ticket eval). Optional.
3. **Reference**: `$PRIMARIS_HOME/growth-plan.md` — user's targets. If missing, Cawl falls back to defaults from `growth-plan.template.md` and prints a one-line note instructing the user to run `/primaris init` (a future, pure-doc init flow — see "Init flow" below).

If the primary source is missing or older than 7 days, `/level-check` halts with a clear message instructing the user to run `/insights` and then re-run `/level-check`.

### `report.html` parsing strategy

The report is structured HTML with stable `id` and `class` attributes:

| Section | Anchor | Cawl maps to |
|---|---|---|
| Stats row | `class="stats-row"` (Messages / Lines / Files / Days / Msgs/Day) | Volume metrics (raw inputs to level scoring) |
| At-a-glance | `class="at-a-glance"` | Initial framing (working / hindering / quick wins) |
| `What You Work On` | `id="section-work"` | Project/domain breadth (Level 2 / 3 signal) |
| `How You Use Claude Code` | `id="section-usage"` | Orchestration patterns (Level 3 / 4 signal) |
| `Impressive Things You Did` | `id="section-wins"` | Strength evidence |
| `Where Things Go Wrong` | `id="section-friction"` | Anti-signals + Tenet violation candidates |
| `Existing CC Features to Try` | `id="section-features"` | Capability gaps |
| `Suggested CLAUDE.md Additions` | `class="claude-md-section"` | Context-engineering signal (Level 2 indicator) |
| `New Ways to Use Claude Code` | `id="section-patterns"` | Forward growth direction |
| `On the Horizon` | `id="section-horizon"` | External feature awareness |

Cawl extracts these via Bash + Python regex (`re` only — no third-party HTML parser needed). The 67 KB file parses in milliseconds.

### Level mapping rules

Cawl maps `report.html` evidence to the existing levels rubric (`playbooks/ai-engineering-levels.md`) using these heuristics:

- **Level 2 (Context Engineer)** signals — `Suggested CLAUDE.md Additions` section non-empty (CLAUDE.md being maintained), recurrence of "context piecemeal" friction = anti-signal.
- **Level 3 (Advanced Context Engineer)** signals — friction section mentions of "subagents", "gate review", "ticket-pipeline" = positive; "Prompt is too long" mid-pipeline = anti-signal (single-thread overrun).
- **Level 4 (Hermes Engineer)** signals — at-a-glance / wins mentions of "parallel observer agent", "self-correcting workflow"; absence = neutral, not negative.
- **Tenet violation candidates** — friction section `Premature implementation before approach validation` = Tenet 1 (Prime Directive); `edits reapplied N times` = scope-discipline gap (Tenet 2 candidate).

The mapping rules are documented in the new "Roadmap" subsections of `ai-engineering-levels.md` per level, so Cawl can cite the rubric line by line in its eval reports.

### User-data layout

```
$PRIMARIS_HOME/                            # default ~/.primaris/
├── growth-plan.md                         # user's current state + targets (copied from template at init)
└── eval/                                  # Cawl writes reports here
    ├── 2026-05-08-level-check-30d.md
    └── ...
```

Plugin location remains read-only:

```
plugins/primaris/
├── playbooks/
│   └── growth-plan.template.md            # ship as template, never edit per user
└── eval/                                  # legacy v0.1.0 location, kept empty for backward-compat
```

Cawl writes new reports to `$PRIMARIS_HOME/eval/`, not to the plugin tree. `plugins/primaris/eval/` continues to exist (with `.gitkeep`) so the v0.1.0 layout remains valid for any documentation that referenced it, but v0.2.0 reports no longer land there.

### Init flow

Pure doc-driven, no new command in v0.2.0:

1. User installs plugin via marketplace.
2. README's "First-run flow" instructs:
   ```bash
   mkdir -p ~/.primaris/eval
   cp plugins/primaris/playbooks/growth-plan.template.md ~/.primaris/growth-plan.md
   $EDITOR ~/.primaris/growth-plan.md   # fill in name, current level, targets
   ```
3. User runs `/insights` once in any Claude Code session.
4. User runs `/level-check 7d` from any session.

A future `/primaris init` slash command (Phase 2 candidate) can automate steps 1–3. Out of scope for v0.2.0.

### Backward compatibility

- v0.1.0 had Cawl read `playbooks/bach-growth-plan.md`. v0.2.0 removes the file. Any v0.1.0 install upgrading must run the init flow.
- v0.1.0 had Cawl write to `plugins/primaris/eval/`. v0.2.0 writes to `$PRIMARIS_HOME/eval/`. Old reports are preserved (read by Cawl as historical context if present), new reports go to the new location.
- Ultramarines `/ticket-pipeline` auto-fire of Cawl is unchanged.

## Component design

### `agents/cawl.md` — Cawl rewrite

The Persona, Iron Law, and Tools sections remain. The **Inputs** and **Workflow** sections are rewritten to:

- Document the data source priority (above).
- Replace `state.json` / `log.md` references with `report.html` as the primary path.
- Add a parsing block: a small Bash + Python `re` snippet that Cawl uses to extract each section. The snippet is documented in the agent file so Cawl invokes it consistently.
- Keep the per-ticket and period modes, but redefine "period" in terms of `report.html` data span (the report itself spans a fixed window — usually ~21 days).
- Update report templates to cite `report.html` section IDs as evidence references.
- Replace `playbooks/bach-growth-plan.md` references with `$PRIMARIS_HOME/growth-plan.md`.

### `commands/level-check.md` — `/level-check` rewrite

The frontmatter, doctrine note, and read-only nature stay. The **Flow** is rewritten to:

1. Resolve `PRIMARIS_HOME` (default `~/.primaris`).
2. Check `~/.claude/usage-data/report.html` exists.
   - Missing → halt with: "Run `/insights` first, then re-run `/level-check`." Exit clean.
   - mtime > 7 days → halt with: "Report is stale (last refreshed YYYY-MM-DD). Run `/insights` to refresh, then re-run." Exit clean.
3. Check `$PRIMARIS_HOME/growth-plan.md` exists.
   - Missing → print one-line warning: "No growth plan at $PRIMARIS_HOME/growth-plan.md. Cawl will use defaults. Run init flow to personalise (see plugin README)."
4. Spawn Cawl with `report_path` and optional `growth_plan_path`.
5. Cawl returns report path + console summary.
6. Print summary verbatim. Echo `Full report: $PRIMARIS_HOME/eval/<filename>`.

The Empty state and Examples sections are updated accordingly.

### `playbooks/growth-plan.template.md` — replaces `bach-growth-plan.md`

Generic placeholders, no Bach-specific content. Sections retained:

- Header + tagline + `Last updated:` placeholder.
- `## Current state` — placeholder for level + best-evidence + weakest-evidence.
- `## Strengths to preserve` — empty bullet list, hint to fill from `/insights` `Impressive Things You Did`.
- `## Weaknesses to fix` — empty bullet list, hint to fill from `/insights` `Where Things Go Wrong`.
- `## 30-day targets (review by YYYY-MM-DD)` — placeholder bullets.
- `## 90-day targets (review by YYYY-MM-DD)` — placeholder bullets.
- `## Cawl's working assumptions` — preserved, but the four Bach-specific items are replaced with examples of valid stable preferences. The user is invited to add their own.

### `playbooks/ai-engineering-levels.md` — Roadmap subsections

For each level (0–5), add a third subsection block after `Anti-signals`:

```markdown
**Roadmap to Level N+1**

- *Readiness signals* — concrete behaviours that indicate Bach (you) are ready to claim the next level.
- *Upgrade actions* — 3–5 concrete actions to take in the next 7–30 days.
- *Common blockers* — recurring patterns that pull you back.
```

The intent is twofold: human readability ("how do I level up?") and machine readability (Cawl cites these directly in recommendations).

## Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| `/insights` HTML structure changes between Claude Code versions, breaking parsing. | Parse via stable `id` and `class` anchors; fall back to text-only extraction if structured extraction fails; print a `NOT FOUND` line per missing section instead of crashing. |
| User on a fresh machine has no `report.html` yet. | `/level-check` halts with a clear instruction to run `/insights` first. No silent failure. |
| User did not run init flow → no `growth-plan.md`. | Cawl uses defaults from the template; `/level-check` prints a warning. Eval still produced (lower personalisation). |
| `~/.primaris/` cluttered after months of weekly checks. | Reports are dated in filename; user can prune manually. v0.3.0 candidate: archive flag. |
| Multi-user shared machine. | Out of scope. `PRIMARIS_HOME` env var lets advanced users redirect; documented in README. |
| Old v0.1.0 reports under `plugins/primaris/eval/` orphaned. | Cawl reads them as historical context if present. Not deleted automatically. User can move to `~/.primaris/eval/` manually. |

## Migration from v0.1.0

For any user (including Bach) running v0.1.0 today:

1. Pull the v0.2.0 commits.
2. `mkdir -p ~/.primaris/eval`
3. `cp plugins/primaris/playbooks/growth-plan.template.md ~/.primaris/growth-plan.md`
4. Edit the new growth-plan with whatever was in `bach-growth-plan.md` (the file itself is removed by v0.2.0).
5. Run `/insights` once.
6. Run `/level-check 7d`.

The migration is documented in the v0.2.0 entry of `ROADMAP.md` and the primaris README.

## Success measure for v0.2.0

After 4 weeks of running v0.2.0:

- ≥1 user other than Bach has installed primaris and produced at least one Cawl eval report.
- ≥4 Cawl eval reports cite specific `report.html` section IDs as evidence.
- The `/insights`-driven flow has not regressed any of the v0.1.0 acceptance criteria.

If those three signals hold, Phase 2 (Prime Directive enforcement) starts on a v0.3.0 base.
